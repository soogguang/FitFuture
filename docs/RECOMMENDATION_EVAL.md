# FitFuture 대안 추천 실험 결과

- 실험일: 2026-11-27
- 대상: 맞춤 식단 대안 추천 서버 (`recommendation-server`, `/recommend`)
- 실험 스크립트: `recommendation-server/scripts/eval_recommend.py` (브랜치 `recommend-eval`)
- 원본 결과: 실행한 PC의 `recommendation-server/eval-results/` (요약 md, 요청별·대안별 CSV, Git 제외)

---

## 1. 한 줄 요약

> 실제 Gemini로 **식단 10개 × 사용자 3명 = 30번** 추천을 요청했다. 그 결과로 나온 **대안 31개**를 7가지 규칙으로 모두 검사했고, **31개 모두 7가지 규칙을 전부 지켰다**(217 / 217). 알레르기 근거가 부족한 14건은 대안을 만들지 않고 안내했다.

---

## 2. 무엇을 확인하려고 했나

FitFuture의 대안 추천은 두 단계로 동작한다.

1. **Gemini**가 "밥을 덜 먹기", "소스 줄이기" 같은 대안 후보를 5~10개 제안한다.
2. **서버 규칙**이 후보를 하나씩 검사한다. 식약처 DB로 영양을 다시 계산하고, 예산·알레르기·열량 범위·중복을 확인한다. 통과한 후보를 점수 순으로 최대 3개 보여준다.

AI가 제안한 후보가 이상해도 **규칙이 걸러내는지**, 실제 사용 상황에서 확인하는 것이 목적이다.

| 질문 | 확인 방법 |
|---|---|
| 실제 Gemini로 추천이 안정적으로 나오는가? | 30번 요청의 성공·실패·응답 시간 |
| 나온 대안이 규칙(예산·알레르기·영양 등)을 다 지키는가? | 대안마다 7가지 규칙을 **서버와 별개로** 다시 검사 |
| 목표(감량)에 맞는 대안인가? | 감량 목표면 원래보다 열량이 줄었는지 |
| 같은 요청에 결과가 일정한가? | 같은 요청을 3번 반복 |
| 선호 음식이 반영되는가? | 선호 음식만 바꿔 요청 비교 |

## 4. 실험 방법

1. 식단 10개 × 프로필 3명 = **30번** 추천을 요청한다 (본 실험).
2. 서버가 돌려준 대안(요청당 최대 3개)을 **스크립트가 직접 다시 검사**한다. 서버 결과를 그대로 믿지 않고, 같은 식약처 DB 파일과 알레르기 근거 파일로 따로 계산한다.
3. 추가 실험
   - **선호 반영:** 같은 식단·프로필에서 선호 음식만 "없음 ↔ 있음"으로 바꿔 3쌍 비교
   - **일관성:** 같은 요청을 3번 반복 (돈가스 정식, 짜장면)

### 대안 하나마다 검사한 7가지 규칙

| 규칙 | 뜻 | 통과 조건 |
|---|---|---|
| 영양 재계산 | AI가 아니라 DB로 계산한 값인가 | 식약처 DB × 중량으로 직접 계산한 열량과 ±0.5kcal 이내 |
| 열량 범위 | 너무 적거나 많지 않은가 | 300~1,800kcal |
| 과도한 감량 방지 | 원래 식사를 너무 많이 줄이지 않았나 | 원래 열량의 60% 이상 |
| 예산 | 한 끼 예산을 넘지 않는가 | 가격 ≤ 예산 |
| 알레르기 | 알레르기 성분이 없다는 근거가 있는가 | 모든 음식에 NEIS 근거가 있고, 해당 성분이 없음 |
| 중복 | 비슷한 대안이 두 번 나오지 않았나 | 다른 대안과 전체 중량 차이 5% 이상 |
| 정렬 | 점수 높은 순인가 | 1순위 ≥ 2순위 ≥ 3순위 |

품질 지표로 **감량 목표면 원래보다 열량이 줄었는지**도 따로 봤다.

## 6. 결과 해석

1. **AI 제안이 들어가도 규칙은 100% 지켜졌다.** Gemini가 만든 후보는 서버 규칙을 통과한 것만 사용자에게 보인다. 실제로 보인 대안 31개는 영양·예산·알레르기·열량·중복 규칙을 하나도 어기지 않았다. 영양 수치는 AI 숫자가 아니라 식약처 DB 계산값과 일치했다.
2. **감량 목표에 맞는 방향으로 추천했다.** 감량 목표 사용자의 대안 21개는 모두 원래 식사보다 열량이 낮았다.
3. **"대안 없음" 14건은 실패가 아니라 안전 장치다.** 14건은 모두 알레르기를 입력한 사용자(P2·P3)에서 나왔다.
   - 알레르기 근거 데이터가 없는 음식은 "안전하다"고 가정하지 않고 제외했다. 예: 돈가스, 라면, 치킨.
   - 실제로 성분이 들어 있는 음식도 제외했다. 예: 김치찌개(새우젓 → 갑각류).
4. **추천은 안정적이다.** 같은 요청을 반복해도 1순위가 같았다.
5. **응답이 빠르다.** 평균 2.2초로, 앱에서 기다리기에 무리가 없다.

## 7. 한계와 개선 과제

| 한계 | 내용 | 개선 방향 |
|---|---|---|
| 알레르기 사용자 대안 부족 | 알레르기 입력 시 대안이 나온 비율 30% (6/20) | 알레르기 근거 데이터 확대 (식당 메뉴 성분표 등) |
| 선호 반영 약함 | 선호 음식을 넣어도 순위가 바뀐 경우 1/3 | 서버 점수 규칙 수정: 선호 없음 기본점(12.5점)보다 선호 음식 일부 포함 점수가 낮아지는 문제 |
| 음식이 하나인 식단 | 비빔밥·카레라이스 등은 대안 1개만 나옴 | 양 조절 외 다른 대안 유형(곁들임 추가 등) 검토 |
| 모델 의존 | 기본 모델(3.8-flash)은 지연·한도로 실패 | 모델 선택 기준과 재시도 정책 정리 |
| 실험 규모 | 식단 10 × 사용자 3 | 실제 사용자 기록으로 확대 |

## 9. 다시 실행하는 방법 (Windows)

```powershell
# 터미널 1: 추천 서버 (recommendation-server/.env에 GEMINI_API_KEY, GEMINI_MODEL)
Set-Location recommendation-server
.venv\Scripts\python scripts\server.py --serve

# 터미널 2: 실험
Set-Location recommendation-server
.venv\Scripts\python scripts\eval_recommend.py --delay 15
#   --quick       식단 2개만 (6건)
#   --stop-after  한도 초과가 연속 N번이면 중단 (기본 3)
```
